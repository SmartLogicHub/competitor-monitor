# 淘宝登录页闪烁修复设计

## 问题

点击“打开淘宝登录网页”后，浏览器窗口保持打开，但淘宝页面大约每秒在白屏和内容之间跳动。代码检查确认，手动登录进程在页面存活期间每秒调用一次 `BrowserContext.storage_state()`；该周期与用户观察到的闪烁频率一致。

## 目标

- 登录浏览器打开后不再每秒导出状态。
- 继续使用与采集任务相同的持久化 Chrome 用户目录，使 Cookie 跨程序重启、电脑重启保存。
- 打开页面后识别淘宝的真实状态：检查中、未登录、需要验证、已登录。
- 登录成功时仅导出一次状态；关闭窗口时再做一次兜底导出。
- 控制台展示真实状态，而不是把“已保存凭据”等同于已登录。

## 设计

`BrowserService` 暴露当前手动页面的登录状态检测能力，复用已有 `detect_page_auth_state()`，不主动刷新或重新导航页面。`manual_login.run_taobao_login_browser()` 定时读取状态，但只在状态首次变为“已登录”时调用一次 `persist_storage_state()`；窗口关闭后再尝试保存一次。持久化 Chrome profile 仍是主要会话存储，因此即使最后一次导出因浏览器已经关闭而失败，登录 Cookie 仍由 Chrome 自身保存。

会话状态文件增加 `auth_status`，值限定为 `checking`、`login_required`、`manual_action_required`、`authenticated`。Web API 原样返回该字段，前端映射成中文提示。旧状态文件没有该字段时按 `checking` 兼容。

## 错误处理

- 页面状态读取暂时失败时保留上一次状态，不触发刷新。
- 状态导出失败不关闭登录窗口；持久化 profile 仍然可用。
- 浏览器异常退出时继续记录 `failed` 和错误信息。

## 验证

- 单元测试证明窗口保持打开的多次轮询期间，登录成功只保存一次，关闭时最多再保存一次。
- 单元测试覆盖未登录、人工验证和已登录状态传递。
- 前端测试覆盖状态文案。
- 完整 Python 与前端测试通过后重新构建 Web/TaskRunner，并检查 ZIP 内两个 EXE、按钮资源和部署说明。
